## 核心结论

建议最终建设一个企业 AI 任务工作台：用户提交目标与授权资料，系统持续完成研究、分析和受控行动，交付可修订、可核查的文件与业务结果。平台负责身份、任务状态、权限、预算、审批和产物；执行器负责在这些约束内选择工具并推进任务。

保留观心现有 FastAPI、LangGraph、AI SDK、知识库和写工作流。Deep Agents SDK 是优先实验的复杂任务执行器；Claude Code 提供任务闭环与交互参照；DeepSeek Harness 提供能力模块和事件架构参照。当前证据支持渐进接入，尚不足以决定整体替换核心。

# 技术路线：先把一个任务做完整

## 目标架构与归属

用户入口 → 观心任务控制层 → 可替换执行器 → 受控工具与工作区。任务控制层保存 owner、goal、budget、status、产物与审核结果。执行器可先用现有研究逻辑；未来经适配接入 Deep Agents。业务写操作继续由现有工作流执行，恢复前重新校验权限。

不要让新执行器同时拥有另一套认证、审批和用户可见任务状态。LangGraph checkpoint 保存执行位置；TaskRun 保存业务状态；Artifact 保存结果及版本；关键运行事件用于重连与追溯。先新增最小关联字段和适配接口，不要求第一版把全部历史表迁成事件溯源系统。

## 第一条黄金路径

“读取授权资料和公开来源 → 研究指定问题 → 生成带证据的报告 → 用户提出修改 → 生成新版本 → 形成行动草稿”。这条路径直接复用当前研究与知识库资产，能检验上下文、文件交付与用户复用。具体行业用户尚未确定，该场景是建议起点。

当前普通对话组装仍将全部历史转换为 role/content，工具 UI 恢复不等于模型上下文恢复；研究仍直接在 HTTP 流生成器内执行。建议把最小持久 worker 提前到 v0.3 的试用收口阶段，让关闭页面只影响订阅；v0.4 再做完整上下文压缩、预算分配与执行器优化。[本地执行器](/Users/wyf/workspace/aicoding/guanxin-v2/backend/app/agent/executor.py)、[流接口](/Users/wyf/workspace/aicoding/guanxin-v2/backend/app/api/aisdk.py)

## Deep Agents 实验的硬条件

1. 独立依赖环境，固定发布包与模型；主应用保持可回退。现有锁文件低于候选 LangChain/core 要求，先解析兼容性，再做真实调用。
2. 现有授权工具只是候选的一部分；检查并限制其内置文件工具、子代理和执行工具。多用户存储显式设置租户/用户命名空间，身份由服务端注入。
3. 先使用任务隔离的虚拟工作区，不开放任意 shell。代码执行以后加入独立沙箱；业务凭据由宿主工具持有。
4. 建立事件适配层，保留 AI SDK 的稳定 tool_call_id、审批与产物关联；不要把候选的 Beta v3 stream 当作已有协议的直接替换。
5. 首轮只读研究；真实写入保持单一工作流执行责任，避免双重审批或恢复后重复执行。

来源：[LangChain：Backends](https://docs.langchain.com/oss/python/deepagents/backends)、[工具与权限](https://docs.langchain.com/oss/python/deepagents/overview)、[事件流](https://docs.langchain.com/oss/python/deepagents/event-streaming)，本轮复核于 2026-09-07。文件权限不等于沙箱隔离，检查点也不保证外部事务可回滚。

## 采用决策

12 个复杂任务、每例三次、相同模型与预算，比较基线和候选。权限、恢复、取消、审批关联和产物完整性必须全部通过。质量或返工至少一项明显改善且费用满足预设上限，才扩大试点；收益不明则继续现有实现。本文没有运行这一实验，不能给出性能胜负。

# 迭代计划与最终验收

本页调整上一版的实施顺序；后附 9 月 4 日报告保留原始研究记录。发生冲突时，以本页为准。全部是计划建议，尚未实施。

| 阶段 | 核心交付 | 放行标准 |
| --- | --- | --- |
| v0.3a 最小交付 | TaskRun、Artifact、报告/来源、修订与版本；复用研究逻辑 | 一项任务能完整交付；失败不标成功；产物越权读取被拒 |
| v0.3b 内部试用 | 真实账号、密钥撤销、基本审计与配额；单 worker 持久领取、重连与取消 | 3-5 人可独立使用；页面断开后任务有明确状态；重启恢复与备份演练通过 |
| v0.4 长任务增强 | ContextBuilder、原文卸载、摘要、预算；完成 Deep Agents 对照实验 | 长对话约束可恢复；预算不重置；候选采用/停止有证据 |
| v0.5 业务行动 | 一个真实系统连接；审批具体参数、回执、对账；按需加入代码沙箱 | 重复提交和崩溃不盲目重放写操作；业务结果可查询确认 |
| v0.6 技能与协作 | 有版本的方法包；2-3 个受限子任务；共享预算和取消 | 相比单 Agent 有实测收益；子任务不扩大权限 |
| v1.0 持续交付 | 两个高频场景；质量回归、运维、备份恢复与责任归属 | 连续四周观察使用价值；负责人验收；服务指标由实际使用确定 |

## 首个十个工作日

第 1-2 日确定首批使用者、20 个任务样本与产物验收规则。第 3-5 日完成最小任务记录和报告发布接口；前端展示状态、来源和文件。第 6-8 日打通修订版本、隔离验证与持久 worker 冒烟。第 9-10 日评审完整样本，确认 v0.3b 身份与运维剩余项，并完成 Deep Agents 依赖兼容结论。

这是范围顺序，非承诺日程。新增 worker 前移会增加 v0.3 工作量；上一版两人团队 13-19 周的总估算只能保留为粗略参考，必须按可用人力和明确任务重新估算。不得把单人和双人工作量直接等同。

## 成功看什么

核心指标为任务合格率、引用支持率、人工复核返工时间和每个合格结果的总成本。初始 20 个任务各三次，失败与超时计入分母；单独测试越权、撤权恢复、重复审批、断连、超时、崩溃和写后无回执。多 Agent 数量、消息数和工具数只作诊断。

v1.0 的最终标准是用户持续委托真实工作，系统能在授权和预算内交付、解释失败并交接。任务结束、文件校验通过和用户验收通过应分别记录。
